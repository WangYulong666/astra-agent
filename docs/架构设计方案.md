# Astra Agent —— 通用 Agent 工作台架构设计方案 v2

> **一句话**：CLI agent 跑在隔离 microVM 里，平台做 ACP Client，人在 Web / 桌面 / 手机任意一端下指令、审批、接管、取产出。
> **代号**：Astra Agent。定位：内部生产力工具。
> **硬约束**：全组件源码可得、自行编译、自行部署；平台内核组件只认 OSI 许可。

---

## 0. v2 相对 v1 改了什么

v1 把 Agent 循环放在 Go 控制面，用 PATH 垫片 + PTY 解析拦截危险命令。**这条路是错的**，v2 整体推翻：

| 维度 | v1 | **v2** |
|---|---|---|
| Agent 循环位置 | Go 控制面 | **沙箱内 agent 进程** |
| 传输 | 工具调用走 envd RPC | **ACP（JSON-RPC/NDJSON）** |
| 危险命令拦截 | PATH 垫片 + 正则猜 | **`session/request_permission` 协议级阻塞** |
| 跨网络次数（一轮） | 2 次（工具结果上、指令下） | **1 次（只有 LLM 调用）** |
| 文件读写 | 每次走 envd RPC 搬内容 | **沙箱内本地操作，零跨网络** |
| 长任务 checkpoint | 自己序列化上下文 | **沙箱 pause = VM 内存快照** |
| managed / byo | 两套实现 | **同一套传输，只有镜像和启动参数不同** |

**v1 错在哪**：把"Agent 会做什么"当成平台的责任。实际上成熟的 CLI agent（DeepSeek Harness、Gemini CLI 原生 ACP、Claude Code / Codex 官方适配器）已经比我们写得好，平台的价值在**编排、审批、多端、隔离**，不在自己重写一遍 agent 循环。

## 1. 一页结论

| 层 | 选定 | 理由 | 红线 |
|---|---|---|---|
| Agent 运行时 | **DeepSeek Harness + ACP v1** | 第一方 ACP（`dsh --profile acp`），MIT 可自编译，协议级权限模型 | ✅ MIT |
| Agent 进程位置 | **沙箱内** | 文件操作本地化、pause 即 checkpoint、审批天然回流 | — |
| 沙箱底座 | **CubeSandbox**（Apache 2.0） | KVM microVM，冷启 ~60ms，e2b 协议兼容 | ✅ |
| 沙箱控制面 | CubeAPI `:3000` REST | 创建/暂停/恢复/销毁 | ✅ |
| 工具通道 | **MCP server**（控制面暴露） | ACP 管人机通道，MCP 管工具通道，职责不混 | ✅ |
| 后端 | **Go 1.25 + chi + sqlc/pgx** | 自研 ACP Client（无官方 Go SDK，但 NDJSON 分帧极简） | ✅ |
| 存储 | PostgreSQL 16 + SeaweedFS + Valkey | 账本 / 产出物 / 路由限流 | ✅ |
| 事件总线 | NATS JetStream | 单二进制，匹配 append-only 事件 | ✅ |
| 前端 | React 19 + TS + Vite | 契约单一来源 | ✅ |
| 桌面端 | **Wails v2** | 原生侧 Go，直接复用 ACP client 与事件处理 | ✅ MIT |
| 移动端 | **Expo** | 与 Web 共享 TS | ✅ MIT |

### 1.1 三个硬判断

1. **不要自己写 agent 循环。** 一期用 **DeepSeek Harness 的 ACP profile**（`dsh --profile acp`），自研 ACP server 留到 M4 之后。同时造 agent 和造平台，两个都做不好。
2. **每个会话 = 一个沙箱 = 一个 agent 进程 = 一条 ACP 连接。** 这条连接同一时刻只能由一个 worker 持有——不是"全集群一个 client"（集群有 N 个 worker，各持有不同会话的连接）。多端也不能直连沙箱：一个 agent 只有一路 stdin/stdout，两路 client 接入会让 JSON-RPC id 命名空间冲突、权限请求被任一方抢答。多端只能订阅控制面转发的事件流。
3. **LLM key 不进沙箱。** 沙箱内 agent 的 base_url 指向自建网关，只拿短期租户令牌。真 key 留在控制面。

## 2. 系统架构

```
端       只做交互：渲染、输入、订阅事件
接入层   只做鉴权、限流、协议转换
控制面   唯一有状态：ACP Client、事件落库、审批判定、任务状态机
沙箱层   唯一执行不可信代码：agent 进程 + acp-proxy
```

沙箱层任何节点挂掉，会话状态零损失——状态全在 PG 事件表里，沙箱只是可重建的执行器。

### 2.1 进程拆分

| 二进制 | 职责 | 副本 |
|---|---|---|
| `astra-api` | HTTP/SSE 入口、鉴权、聚合查询 | N |
| `astra-worker` | **ACP Client**：驱动 agent、转发事件、处理权限请求 | N（按 session_id 一致性哈希） |
| `astra-sandboxd` | 沙箱池：预热、健康检查、回收 | 1（选主） |
| `astra-gateway` | LLM 网关 + MCP server | N |

**同一个会话的 ACP 连接只能由一个 worker 持有**：ACP 是单客户端独占会话，两个 worker 连同一个 agent 会让 `session/update` 交错、`request_permission` 抢答。用 PG advisory lock 按 `session_id` 保证。

### 2.2 绑定关系：1 会话 = 1 沙箱 = 1 agent = 1 条 ACP 连接

| 关系 | 基数 | 说明 |
|---|---|---|
| Session → Sandbox | 1 : 1（活跃期） | 会话创建时分配，销毁时回收 |
| Sandbox → Agent 进程 | 1 : 1 | 沙箱内只跑一个 agent，不做多实例复用 |
| Sandbox → acp-proxy | 1 : 1 | proxy 随沙箱启动，只桥接这一个 agent |
| ACP 连接 → worker | 1 : 1（同一时刻） | 每个会话的连接由唯一一个 worker 持有 |
| Worker → 会话 | 1 : N | 一个 worker 并发持有多条连接，每会话一条独立 WSS |

**为什么不能一个沙箱跑多个会话**：agent 的模型上下文、文件系统、shell 状态都是会话私有的。共用沙箱等于把两个人的工作区叠在一起，隔离边界直接失效。

**为什么不能一个会话跑多个 agent**：没有场景。要并行就开多个会话，而不是在一个会话里塞多个 agent——上下文互相污染，审批也无法归属到具体责任人。

**Session 与 Sandbox 不是永久绑定**：沙箱崩溃 / 空闲回收 / 模板升级时会重建，**session 不变，只换 sandbox_id**。历史落 `session_sandbox_history`，用于审计与产出物溯源。

**worker failover**：

```
worker 崩溃 → 它持有的所有会话转 reconnecting
           → lease（15s）过期，其他 worker 抢到 advisory lock
           → 重连该会话的 proxy（agent 还在沙箱里活着，会话就在内存里）
           → 直接继续，**不需要 resume**
           → 只有沙箱/agent 也重启过，才用 session/resume 从持久化存储恢复
```

一条会话的 ACP 连接始终只有一条，worker 之间是"接管"而不是"共享"。

## 3. ACP 运行时（核心）

### 3.1 协议事实（已核实）

| 项 | 事实 |
|---|---|
| 编码 | JSON-RPC 2.0，UTF-8 |
| 分帧 | **NDJSON**：每行一条消息，`\n` 分隔，**禁止内嵌换行**（不是 LSP 的 Content-Length） |
| 传输 | 规范只定义 stdio；Streamable HTTP 仍是 draft；**但明确允许自定义传输** |
| 版本 | `protocolVersion: 1` 稳定，v2 experimental —— **锁 v1** |
| Agent 侧方法 | `initialize`、`auth/login`、`session/new`、`session/prompt`、`session/list`、`session/load` / `session/resume`、`session/close` |
| Client 侧方法 | **`session/request_permission`**、`fs/read_text_file`、`fs/write_text_file`、`terminal/*`、`elicitation/create` |
| 通知 | 上行 `session/cancel`；下行 `session/update` |
| 约束 | agent 的 stdout **只能**输出 ACP 消息；日志必须走 stderr |

**`session/update` 的 update 类型**（v2 规范命名，v1 略有差异，以锁定版本为准）：

| update 类型 | 含义 | 落到事件表 |
|---|---|---|
| `agent_message_chunk` | 回复正文增量 | `message_delta` |
| `agent_thought_chunk` | 思考过程增量 | `thought_delta`（前端可折叠） |
| `tool_call` | 工具调用开始（含 `kind`） | `tool_call_start` |
| `tool_call_update` | 状态/内容变更 | `tool_call_progress` |
| `tool_call_content_chunk` | 工具输出增量 | `tool_output_delta` |
| plan / config 类 | 计划、可用命令 | 原样存 `payload` |

`tool_call.kind` 取值：`read` / `edit` / `delete` / `move` / `search` / `execute` / `think` / `fetch` / `other` —— **这个字段直接用于风险分级**，比 v1 的正则猜命令可靠得多。

### 3.2 为什么必须在沙箱内放 acp-proxy

如果 worker 直接 `exec` agent 并接管 stdio pipe，会有两个致命问题：

1. **pipe 不可重连**。worker 重启 → pipe 断 → agent 进程变孤儿，会话永久失联
2. **agent 生命周期绑死 worker**。worker 扩缩容会杀掉正在跑的长任务

解法：沙箱内跑一个薄 proxy。

```
agent 进程  ──stdio(NDJSON)──►  acp-proxy :8080  ◄──WSS(NDJSON)──  worker
```

proxy 职责只有三件（~200 行 Go）：

| 职责 | 说明 |
|---|---|
| 拉起 agent 子进程 | 按模板配置的 `acp_command` 启动，接管 stdin/stdout，stderr 单独转发 |
| stdio ↔ WSS 双向透传 | 逐行转发，不解析 JSON（保持协议无关） |
| 单客户端互斥 | 一个沙箱只服务一条 ACP 连接；新 worker 抢占时旧连接收到 409 |

**恢复分两种情况，已实测区分（2026-10-28）**：

| 场景 | 需要 resume？ | 原因 |
|---|---|---|
| worker 崩溃后重连 proxy | **不需要** | proxy 与 agent 在沙箱里独立存活，会话仍在 agent 内存中。dsh 对这种情况返回 `session is already active`，这是正确行为 |
| 沙箱重建 / agent 进程重启 | **需要** | 会话不在内存里了，`session/resume(sessionId)` 从持久化存储恢复执行态。已实测通过 |

**历史始终由我们的 PG 事件表提供**——agent 不拥有第二份真相，proxy 也不缓存帧。
重放依赖 agent 日志完整，而事件表是平台自己的资产，这条比"让 agent 重放"更可靠。

### 3.3 Go 侧 ACP Client 骨架

```go
package acp

// 一帧 NDJSON
type frame struct {
    JSONRPC string          `json:"jsonrpc"`
    ID      *int64          `json:"id,omitempty"`
    Method  string          `json:"method,omitempty"`
    Params  json.RawMessage `json:"params,omitempty"`
    Result  json.RawMessage `json:"result,omitempty"`
    Error   *rpcError       `json:"error,omitempty"`
}

type Client struct {
    conn    *websocket.Conn      // 到 acp-proxy
    writeMu sync.Mutex           // NDJSON 必须整行写，否则帧被撕裂
    nextID  atomic.Int64
    pending sync.Map             // id -> chan *frame
}

func (c *Client) readLoop() {
    sc := bufio.NewScanner(c.conn)
    sc.Buffer(make([]byte, 0, 256<<10), 16<<20)   // 单帧上限 16MB，diff 可能很大
    for sc.Scan() {
        line := bytes.TrimSpace(sc.Bytes())
        if len(line) == 0 {
            continue                                   // 空行丢弃
        }
        var f frame
        if err := json.Unmarshal(line, &f); err != nil {
            c.log.Warn("bad acp frame", "raw", truncate(line, 256))
            continue                                   // 脏帧不 panic，agent 不该写非 ACP 内容但现实会
        }
        switch {
        case f.Method != "" && f.ID != nil:   // agent → client 请求（权限、fs、terminal）
            go c.serveRequest(&f)
        case f.Method != "":                  // 通知（session/update）
            c.onUpdate(&f)
        default:                              // 响应
            c.deliver(&f)
        }
    }
}

// 单帧写入必须加锁，且只能有一个 \n 结尾
func (c *Client) write(f *frame) error {
    b, err := json.Marshal(f)
    if err != nil {
        return err
    }
    c.writeMu.Lock()
    defer c.writeMu.Unlock()
    _, err = c.conn.Write(append(b, '\n'))
    return err
}
```

**三个坑**：

| 坑 | 后果 | 处理 |
|---|---|---|
| `bufio.Scanner` 默认 64KB 上限 | 大 diff / 文件内容帧被截断，`ErrTooLong` | 必须 `sc.Buffer(_, 16MB)` |
| 多 goroutine 并发写同一连接 | 两帧交错，JSON 解析失败 | 写锁 + 整行 `Write` |
| agent 往 stdout 打日志 | 污染协议流 | 启动参数强制日志走 stderr；proxy 把 stderr 转发到 `run_events` 的 `agent_log` 类型 |
| 一个 worker 持 N 条连接 | 每连接一个 Scanner + 读写 goroutine，N 大时内存与 fd 不可控 | buffer 初始 256KB 按需增长（不要预分配 16MB）；**单 worker 连接数硬上限（建议 200）**，超出由一致性哈希迁移到新 worker |

**连接数与 worker 扩容**：worker 的副本数应该按"会话数 / 200"算，而不是按 CPU 算。一条 ACP 连接绝大部分时间是在等 LLM 返回，几乎不占 CPU——用 CPU 指标扩缩容会严重欠配。这是 worker 和 api 不能共用 HPA 指标的原因。

### 3.4 审批：协议级阻塞，不是事后审计

`session/request_permission` 是 agent → client 的 JSON-RPC **请求**（带 id，必须回复），这天然就是一个阻塞点：

```go
func (c *Client) serveRequest(f *frame) {
    switch f.Method {
    case "session/request_permission":
        var p PermissionParams
        json.Unmarshal(f.Params, &p)

        // 1. 落审批记录（此时 Run 尚未阻塞，先把记录写进去防丢）
        ap := c.db.CreateApproval(ctx, Approval{
            RunID:   c.runID,
            Title:   p.Title,
            Detail:  p.Description,
            ToolCall: p.Subject,        // 含 kind，直接用于风险分级
            Options: p.Options,         // allow_once / allow_always / reject_once / reject_always
            Status:  "pending",
        })

        // 2. Run 转 waiting_approval，推事件给三端
        c.runs.Transition(ctx, c.runID, StatusWaitingApproval)
        c.events.Append(ctx, Event{Type: "approval_req", Payload: ap})

        // 3. 阻塞等人工决定；超时按拒绝处理（安全默认）
        var opt string
        select {
        case opt = <-c.approvals.Wait(ap.ID):
        case <-time.After(c.approvalTimeout):       // 默认 30min，可配
            opt = "reject_once"
        case <-c.ctx.Done():
            return                                          // 连接断了，不回复
        }

        // 4. 回复 agent —— 格式按 ACP 规范
        c.write(&frame{
            JSONRPC: "2.0", ID: f.ID,
            Result: mustJSON(map[string]any{
                "outcome": map[string]any{"outcome": "selected", "optionId": opt},
            }),
        })
        c.runs.Transition(ctx, c.runID, StatusRunning)
    }
}
```

**这个机制的价值**：agent 自己在执行危险动作前会请求权限（配合 agent 的 autonomy 配置）。平台不需要猜命令，`tool_call.kind == "execute"` 就该问。v1 的正则方案在这里彻底不需要了。

自动批准的规则（三级）：

| 情形 | 处理 |
|---|---|
| `kind` ∈ {read, search, think} | 自动批准，记审计 |
| `kind` ∈ {edit, fetch} 且路径/域名在白名单 | 自动批准，记审计 |
| `kind` ∈ {execute, delete} 或命中黑名单 | 挂起等人 |
| 同一 `optionId` 在本次 Run 内被"always allow"过 | 后续自动复用决策 |

### 3.5 工具通道走 MCP，不塞进 ACP

ACP 只解决"人机对话"，agent 的内置工具（读写文件、跑命令）由 agent 自己实现，**平台不该重复提供**。平台独有的能力（产出物归档、受控 web_fetch）用 MCP server 暴露：

```
session/new 时，控制面把 mcpServers 配置塞进参数
  → agent 连到控制面的 MCP server（HTTP/SSE）
  → 调用 publish_artifact / web_fetch 时回到控制面执行
```

这样职责清晰：**ACP 管外层（人机），MCP 管内层（工具）**。两者用同一套 JSON-RPC 语义，但不混。

### 3.6 Agent 选型：DeepSeek Harness

**一期选定 DeepSeek Harness（dsh），`dsh --profile acp` 启动。**

| 项 | 事实 |
|---|---|
| 项目 | `deepseek-ai/deepseek-harness`，MIT，2026-08 开源，当前 v0.2.1-rc.x（**仍是预发布**） |
| ACP 支持 | **第一方**插件 `@deepseek-ai/dsh-acp`，不是第三方适配器 |
| 启动 | `dsh --profile acp`（另有 `web` 带 UI、`headless` 单次任务后退出） |
| 传输 | NDJSON over stdio，日志严格走 stderr |
| 会话 | 支持**跨进程重启的 list / resume / close**；**刻意不做** delete、fork、transcript 回放、附加目录 |
| 模型 | 会话级选 provider / model / reasoning effort |
| MCP | `session/new` 时挂载，stdio + streamable HTTP |
| 权限 | 三档预设 `read-only` / `workspace-write` / `danger-full-access`，每档是「沙箱 + 审批」成对定义 |
| 运行时 | Node ≥ 22.15（源码构建需 ≥ 24.2），npm 包 `@deepseek-ai/dsh` |

**选它而不是 Gemini CLI 的四个理由**：

1. **MIT 且可自行编译**——不依赖 Google 的发布节奇，符合"全组件源码可控"
2. **中文模型优先**——默认 route 到 DeepSeek，token 成本比 Claude / Gemini 低一个量级
3. **插件化内核**——未来平台专属能力（产出物上报、租户配额）可以写成 DSH 插件，比只能走 MCP 更深入
4. **第一方 ACP**——不需要"适配器 + npx 拉包"，离线镜像简单

**"不做 transcript 回放"是优势不是缺陷**：

dsh-acp 刻意只提供标准 ACP v1 界面，不提供 DSH 专属呈现（plan 卡片、todo、标题）和 transcript 回放。意味着：

- 历史**只能**由我们的 PG 事件表提供——本来就这么设计（§4），零冲突
- 重连用 `session/resume` 恢复执行状态，前端从 `run_events` 重建视图
- 好处：agent 不再拥有"历史的第二份真相"，重启后前端看到的和库里必然一致

代价：一期拿不到 plan / todo 的结构化展示，UI 要自己从 `session/update` 拼。可接受的技术债。

**权限预设怎么映射到我们的审批**（最省事的地方）：

| DSH 预设 | 含义 | 平台策略 |
|---|---|---|
| `read-only` | 只能读 | 自动批准只读工具，写操作直接拒 |
| `workspace-write` | bash / 写文件限定在 cwd | **默认**。越界时 dsh 自己发 `request_permission` |
| `danger-full-access` | 关闭沙箱与审批 | **永不使用**。VM 已是隔离边界，这一档等于放弃内层防线 |

关键：**dsh 的 workspace-write 已做了内层约束，我们的审批只兜外层**（越权、出网、危险命令）。这是纵深防御，不是重复。

**不用哪些第三方包**：

| 包 | 为什么不用 |
|---|---|
| `@jeremy9682/dsh-acp` | 权限是 **auto-answer**（自动答），等于没有人工审批；无 resume、无 MCP 挂载 |
| `@openma/deepseek-harness-acp` | 功能最全（load/resume、图片、steering），但第三方 beta。**留作二期备选** |
| `hanxu131-dshacp` | 方法覆盖更广，但刻意不实现 `fs/`、`terminal/`、`session/set_mode` |

一期只用官方包。需要更丰富的呈现（plan / todo / usage）时，再评估 `@openma` 那个。

#### 3.6.1 体积实测与裁剪（2026-10-28 实测，方案落地在 `dsh-trim/`）

**先纠正一个反复出现的误判**：跨平台安装体积差异没有想象中大，且「镜像大小」与「落盘大小」必须分开看。

| 口径 | 数值 | 说明 |
|---|---|---|
| macOS arm64 落盘 | 844MB / 306 包 | 含 `libreoffice-kit-darwin-arm64` 148MB、`sherpa-onnx-darwin-arm64` 33MB |
| **linux/x64 落盘** | **826MB / 614 包** | 与 macOS 只差 18MB —— linux 用 146MB 的 `libreoffice-kit-wasm` 顶替了 148MB 的 darwin 原生版 |
| docker 层（压缩） | 约 150MB（推算） | 按裁剪后 18% 压缩率反推，全量未单独实测；docker 层按压缩存储，这才是镜像仓库与拉取看到的数字 |
| **裁剪后落盘** | **138MB / 187 包 / 11645 文件** | 见下 |
| **裁剪后压缩层** | **25MB** | 七项裁剪 + zod 去重 |

⇒ 之前表格里的「223MB」是压缩量被当成了落盘量，两个口径混用导致结论偏差，此处以实测为准。

**裁剪后三个候选的真实对比**（同一口径：linux/x64 落盘 / 压缩层）：

| CLI | 落盘 | 压缩层 | 需 Node | ACP 接入方式 |
|---|---|---|---|---|
| **DeepSeek Harness（裁剪后）** | **138MB** | **25MB** | 是（≥22.15，+110MB） | 第一方插件 `dsh --profile acp` |
| CodeBuddy Code | 68MB（全平台）→ ~28MB 裁后 | ~20MB | 是 | 内建 `codebuddy --acp`（隐藏参数） |
| Claude Code | 293MB（单 native 二进制） | 126.6MB | **否** | 需适配器 + claude-agent-sdk |

**裁剪的关键不是功能取舍，而是 zod**：46 个 dsh 插件对 `zod` 声明精确版本 `4.4.3`，顶层装的是 `4.6.7`，npm 为每个插件嵌入一份副本 —— **46 × 7MB = 322MB**。一个 `"overrides": { "zod": "4.4.3" }` 就省掉 315MB，比全部功能裁剪加起来还多。4.4.3 满足全部 6 处 range 声明，`verify-acp.mjs` 跑通证明无 API 差异。

七项功能裁剪再省 373MB：Office 转换 −146、语音 −32、sharp-wasm −8、**OTel 遥测 −28**、多厂商 LLM SDK −73、Web UI/experimental −63、跨平台二进制 −24。

**遥测必须单独强调**：`dsh-otel` 默认 endpoint 是 `https://dsh-otel-collector.deepseeksvc.com/v1/logs` —— 默认把沙箱内 trace 发往官方收集端。这是合规项，不是优化项。

**裁剪后的能力边界**（裁剪前就存在，非裁剪导致）：`promptCapabilities` 为 `image:false`、`audio:false`、`embeddedContext:false`，MCP 仅 `http`（无 sse），无 `loadSession` 但有 `resume`/`list`。⇒ 端侧若要传图/附件，只能落盘让 agent 调工具读，不能走 ACP 原生 image block；断线恢复用 `session/resume`。

验证口径：`initialize` → `session/new`（触发 schema 校验 + session 持久化）→ `prompt`（仅因无 API key 停止）。方案文件见 `dsh-trim/`（Dockerfile / package.json / trim.sh / trim-patch.yml / verify-acp.mjs）。

**CodeBuddy 的裁剪点很明确**：68MB 里 `vendor/ripgrep` 占 53MB，是**五个平台各一份**（x64-win32 12MB、x64-linux 11MB、x64-darwin 11MB、arm64-darwin 10MB、arm64-linux 9.4MB）。沙箱只需 `x64-linux` 一份，其余可删。

**实测 `codebuddy --acp` 握手结果**（本机 v2.177.1，隐藏参数，help 未列出）：

```json
{"protocolVersion":1,"agentCapabilities":{
  "promptCapabilities":{"image":true,"embeddedContext":true},
  "mcpCapabilities":{"http":true,"sse":true},
  "loadSession":true},
 "authMethods":[{"id":"external"},{"id":"internal"},{"id":"selfhosted"}]}
```

能力面**比 dsh 更全**（`loadSession: true`，dsh 刻意不做 transcript 回放）。但三个坑：

1. **`--acp` 是隐藏参数**，help 里没有 → 非公开契约，升级可能消失
2. **`--acp` 会额外监听本地端口**（实测 stderr `EADDRINUSE 127.0.0.1:59263`）→ 沙箱内要与 acp-proxy 错开端口
3. **认证走外部**（Google/Github、微信、企业域名）→ 沙箱内需注入短期 token，且要能出网到认证端点

**选型定案（2026-10-28 决定：dsh + 裁剪）**：

| 维度 | 结论 |
|---|---|
| 体积 | 裁剪后 **138MB 落盘 / 25MB 压缩层**，与 CodeBuddy（~28MB / ~20MB）同量级 ⇒ 体积不再是 dsh 的短板 |
| ACP 成熟度 | CodeBuddy 更全（image / embeddedContext / loadSession / sse）；dsh 保守（全 false、仅 http）但满足代码执行场景 |
| **源码可控红线** | **只有 dsh 是 MIT 开源可编译** ⇒ 这是唯一决定项 |

⇒ **定 dsh。** 裁剪把唯一短板（体积）压到 25MB 压缩层，红线优势保留。CodeBuddy 留作二期切换目标 —— 传输层统一在 ACP，换 agent 不动架构。

### 3.7 断线恢复

| 断在哪 | 恢复方式 |
|---|---|
| 多端 ↔ 控制面 | SSE `after_seq` 续传，无影响 |
| **worker 崩溃** | lease 过期 → 其他 worker 抢锁接管 → 重连该会话的 proxy → **agent 未重启，直接继续** |
| **沙箱重建 / agent 重启** | 新沙箱（session 不变、换 sandbox_id）→ `session/resume(sessionId)` 从持久化恢复 |
| worker ↔ acp-proxy | 重连 proxy 即可；历史从 `run_events` 重建，不依赖 agent 回放 |
| acp-proxy ↔ agent | proxy 重启 agent，从最近 `checkpoint` 事件重建 prompt |
| 沙箱整个挂了 | 新建沙箱（**session 不变，换 sandbox_id**）→ 恢复 volume → 重新 `session/new` + 注入历史摘要 |

重连需要的元数据（sessionId、protocolVersion、agentCapabilities）必须落 PG，否则新 worker 接不上：

```sql
ALTER TABLE sessions ADD COLUMN acp_session_id    text;
ALTER TABLE sessions ADD COLUMN acp_protocol_ver  int;
ALTER TABLE sessions ADD COLUMN acp_capabilities  jsonb;
```

### 3.8 沙箱 pause 作为免费 checkpoint

CubeSandbox 的 pause 是 VM 内存快照（CubeCoW），**整个 agent 进程树被冻结**，包括模型上下文、文件句柄、shell 状态。恢复后从原处继续，不需要序列化任何东西。

这让"长任务"的实现成本降到接近零：

```
Run 空闲 5min → pause（内存落盘）
新指令到达   → resume（数十 ms）→ 继续
```

v1 方案里要自己实现的 context checkpoint、工具输出序列化、恢复重放，这里全省了。**这是"agent 放沙箱"最大的隐性收益**，比审批那块更值钱。

## 4. 事件流

设计原则不变：**事件先写 PG，推送只是加速通知**。ACP 让这件事更简单——`session/update` 本来就是通知流，逐条落库即可。

```sql
CREATE TABLE runs (
    id           uuid PRIMARY KEY,
    session_id   uuid NOT NULL,
    org_id       uuid NOT NULL,
    status       text NOT NULL,
    next_seq     bigint NOT NULL DEFAULT 1,
    created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE run_events (
    run_id     uuid   NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
    seq        bigint NOT NULL,
    type       text   NOT NULL,   -- message_delta|thought_delta|tool_call_start|tool_output_delta|approval_req|artifact|checkpoint|agent_log|error
    payload    jsonb  NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (run_id, seq)
);
```

seq 分配（无锁、无间隙）：

```sql
UPDATE runs SET next_seq = next_seq + 1 WHERE id = $1 RETURNING next_seq - 1;
```

订阅：

```
GET /v1/runs/{id}/events?after_seq=42
Accept: text/event-stream
```

| 特性 | 实现 |
|---|---|
| 断线续传 | 客户端带 `after_seq` |
| 多端同时看 | 无状态 fanout，各端独立订阅 |
| 回放 | `after_seq=0` |
| 背压 | 单连接缓冲 512 条，超了断开让其重连续传 |
| 高频 delta 合并 | `message_delta` 按 50ms 窗口合并再落库，避免一次回复写几千行 |

**注意**：`agent_thought_chunk` 和 `tool_call_content_chunk` 是高频流，**必须先合并后落库**，否则事件表会被单个长任务打爆。

## 5. Run 状态机

```
queued ──► running ──┬──► completed
   │           │  ▲   ├──► failed
   │           │  │   └──► cancelled
   │           ▼  │
   │    waiting_approval ──(拒绝)──► running（拒绝原因回灌 agent）
   │           │
   └───────────┴──► paused ──(resume)──► running
```

不变量（代码断言，不靠约定）：
- `completed/failed/cancelled` 终态不可逆
- 同一 Session 只能有一个 worker 持有（PG advisory lock on session_id）
- `waiting_approval` 时 worker 仍持有 ACP 连接（**不能断开**，断了请求就没人回复）
- 一个 ACP session 同时只能有一个进行中的 `session/prompt`；新指令要排队

## 10. 安全

| 面 | 措施 |
|---|---|
| 沙箱隔离 | KVM microVM，VM 级隔离 |
| 出网 | 白名单默认拒（`PUT /sandboxes/:id/network`），agent 的 LLM 只允许到网关 |
| LLM 密钥 | 真 key 在网关，沙箱只拿短期租户令牌（可撤销、可限额） |
| 危险操作 | `request_permission` 协议级阻塞 + 超时默认拒绝 |
| ACP 通道 | proxy 端口需 token 鉴权，禁止裸暴露 |
| 审计 | 所有 `tool_call`、所有审批、所有出网请求落 `audit_logs` |

**一个新风险**：agent 在沙箱内自己读文件，平台看不到它读了什么。缓解：靠 `tool_call` 事件的 `kind=read` + 路径审计，但**无法保证 agent 不绕过**（它可以直接 `cat` 而不发 tool_call）。这是"agent 放沙箱"的固有代价，接受它——因为隔离边界在 VM，敏感数据本来就不该进沙箱。
