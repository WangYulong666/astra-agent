## 一句话结论

**AI 工作台的内核是真的，平台的管理面还没有。**

按「一个能跑通、能演示、代码可读的 agent 工作台」衡量，完成度约 **80%**；
按「一个可交付给企业、能计费能管人能监控的云原生开发平台」衡量，完成度约 **30%**。

差距不在核心链路上，全部集中在「平台治理」这一层——而这一层恰好是商业化必须的。

## 二、已经做实的部分（这部分质量不低）

1. **1 会话 = 1 沙箱 = 1 agent 进程 = 1 条 ACP 连接**——不是 PPT 上的约束，是代码里贯穿的约束：`Create` 的 ID 由调用方按会话维度给出，provider 不得自行编造。
2. **ACP v1 全链路**：NDJSON 编解码、双向请求路由、`session/request_permission` 真阻塞、`session/resume` 跨重启恢复。
3. **审批是真的会停住**：`ask` 策略下越界操作挂起等人点，超时 10min 按拒绝并记 `timeout`，取消时先结审批再发 cancel。这条我用无头浏览器真点过「允许」，run 从 `waiting_approval` 走到 `completed`。
4. **事件流可续传**：SSE `?after_seq=` 断线重连，事件先落库再推送。
5. **三类沙箱 provider 同一接口**：`local`（宿主机进程 + `sandbox-exec`）真验证过、`applecontainer` 有完整实现、`cube` 有 HTTP 客户端但**从未真机验证**。
6. **46 个测试全绿**，跑 3 遍无 flake；真机 dsh + DeepSeek 端到端跑通（1+1 用时 0.93s，写并跑 Python 3.6s）。

这些不是脚手架，是能交付的代码。

## 三、你问的六项：逐条回答

### 3.1 沙箱管理——**有内核，无管理面（15%）**

| 能力 | 状态 |
|---|---|
| provider 抽象（Create/Acquire/Destroy/List） | ✅ 有，接口设计合理 |
| 沙箱列表 / 销毁的命令行 | ✅ `astra-sandbox` CLI 可 `make dev-ls` / `make dev-rm` |
| 沙箱的 HTTP 管理 API | ❌ **没有**。18 条路由里没有 `/v1/sandboxes` |
| 沙箱池化 / 预热 / 复用 | ❌ 没有，一会话一沙箱，用完即毁 |
| 资源配额（CPU/内存/磁盘） | ❌ 没有，`Options` 里无此字段 |
| TTL / 空闲回收 | ❌ 没有，只有会话删除时连带销毁 |
| 沙箱健康巡检 / 孤儿清理 | ❌ 没有后台 reconciler |

**关键判断**：沙箱生命周期目前完全寄生在会话生命周期上。一旦要「一个用户 50 个沙箱、超 30 分钟不活跃自动回收」，现有结构得改。

### 3.2 服务监控——**基本为零（8%）**

| 能力 | 状态 |
|---|---|
| `GET /healthz` | ✅ 返回 `{"status":"ok"}`，仅此 |
| Prometheus metrics | ❌ `go.mod` 无 client，全仓 `internal/` 无 `metrics` 字样 |
| 结构化日志 | ❌ 用的是 `log.Printf` 纯文本，无字段、无级别、无 trace id |
| 链路追踪 | ❌ 无 OpenTelemetry |
| 审计日志 | ❌ 无（谁在什么时候让 agent 执行了什么，查不到） |
| 告警 / 看板 | ❌ 无 |

⚠️ **`deploy/k8s/base/*.yaml` 里给 worker/api 都开了 `metrics: 9090` 端口，但没有任何进程在监听它。** 这是清单与代码脱节，k8s 部署上去会是一个假端口。

### 3.3 大模型 API 管理——**几乎没有，且有架构债（5%）**

现状：`astra-server` 从自己的环境变量读 `DEEPSEEK_API_KEY`，原样转发进沙箱进程的 env，dsh 自己去读。

由此带来四个硬限制：

1. **无法多供应商 / 多模型**：只有一份 key，模型选择硬编码在 dsh 启动参数里。
2. **无虚拟 key、无按会话限额**：没法给某个租户发一个可撤销、可限流的短期令牌。
3. **key 明文进沙箱**：agent 的 bash 工具执行一句 `env` 就能读到真 key——**模型自己就能把 key 泄漏出去**。
4. **无用量采集**：`internal/acp/types.go` 与 `internal/store/types.go` 里连 `usage` / `token` 字段都没有。

第 3 点尤其要注意：`docs/架构设计方案.md` 里明确写了「**LLM key 不进沙箱**，沙箱内 agent 的 base_url 指向自建网关，只拿短期租户令牌，真 key 留在控制面」，第 635 行还把这条列为安全设计要点。**当前实现与自家设计文档直接冲突**，属于需要显式记录的技术债，不是小疏忽。

### 3.4 计费——**零（0%）**

无 usage 记录、无价格表、无账单、无预付费/后付费、无余额。连计费所需的原始数据（每次 run 消耗多少 token）都没有采集，所以这一项不是「差一点」，是「从数据源头就没开始」。

补齐路径：先在 ACP 事件里抓 usage → 落 `usage` 表 → 再谈定价。第一步就要动 ACP 类型和 store schema。

### 3.5 用户权限——**零（0%）**

- `internal/api/*.go` 里 `Authorization` / `Bearer` / `middleware` **一个都没有**，18 条路由全部裸奔，任何能访问 `:7788` 的人都能列出所有会话、读所有产物文件、替任意 run 批准权限。
- `internal/store` 只有 `Session` / `Run` / `Event` 三个实体，**没有 User / Tenant / Org / ApiKey / Role**。
- 无 RBAC、无租户隔离、无审计。
- `deploy/k8s/apisix/` 里配了 JWT 插件，但后端不解析身份，等于网关单方面鉴权、后端仍然信任任何人。

本地单机演示没问题，**一旦多用户就是安全事故**。

### 3.6 OpenAPI——**零（0%）**

- 仓库里**不存在** `contracts/openapi.yaml`。
- 全仓搜 `openapi` 只命中 2 处，都在设计文档里（`docs/架构设计方案.md:534` 把它称作「契约枢纽」，`docs/history/架构设计方案-v1-已被否决.md` 里是目录树示例）。
- 无 swagger UI、无 `oapi-codegen`、无前端类型生成。

接口契约目前**只存在于 Go 的 handler 签名和前端手写的 `web/src/types.ts` 里**，两边靠人肉同步。这是 M1 阶段为了速度做的取舍，但接口已经从 8 条长到 18 条，再不收敛会开始出错。

## 四、前后端「完整」吗

**不是一句「完整 / 不完整」能答的，要分端看。**

| 端 | 状态 |
|---|---|
| Web 前端 | ✅ 工作台本体完整：会话列表、对话流、工具卡片、审批卡片、文件面板、停止、重发、离线横幅。**但只是单页工作台**——无路由、无登录页、无设置页、无管理后台、无监控页 |
| Go 后端 | ✅ 核心链路完整且质量不错；❌ 缺少全部平台层（认证、租户、配额、计量、审计、指标） |
| 桌面端（Wails） | ❌ 未开始（M2） |
| 移动端 | ❌ 未开始（M3 只有单机审批，多人流转没做） |
| K8s 部署 | ⚠️ 清单骨架齐全（737 行，含 StatefulSet/APISIX/CubeSandbox values），但镜像 `PLACEHOLDER`，**从未真部署过** |
| 持久化 | ⚠️ 文件 JSON store（`internal/store/file.go`），**单副本**。审批注册表在内存，多副本必然失效 |

所以准确说法是：**「单机版的 Web 工作台」是完整的；「云原生开发平台」不是。**

## 五、被低估的风险

1. **key 明文进沙箱**（上文 3.3）——与自家 ADR 冲突，且是可被模型主动触发的泄漏面。
2. **全裸 API**——`0.0.0.0` 一旦监听到外网，所有会话内容可被任意读取。
3. **单副本假设散落在代码里**——store 是文件、审批在内存、事件 seq 靠本地锁。多副本不是「加个 Deployment 副本数」就能成立的。
4. **`cube` provider 从未真机验证**——生产方案的地基是没踩过的。
5. **前端零测试**——`timeline.ts` 里的事件折叠逻辑（四类块的状态机）是最容易回归的地方，却没有一个测试。

## 六、如果继续做，建议的顺序

按「投入产出比 × 阻塞关系」排，不是按重要性排：

| 顺序 | 事项 | 为什么排这个位置 |
|---|---|---|
| 1 | **补认证 + 租户字段** | 一切治理的地基。没有 `tenant_id`，后面的配额、计费、审计全都无处挂载 |
| 2 | **换 PG 存储** | 文件 store 一旦有并发写入和多副本就崩。越晚改成本越高（现在只有 3 个实体） |
| 3 | **OpenAPI 契约 + 生成** | 接口 18 条了，现在收敛还来得及；再涨一倍就是手工地狱 |
| 4 | **LLM 网关 + 虚拟 key** | 一次解决 3 个问题：key 不进沙箱、可多模型、把 usage 采到 |
| 5 | **metrics + 结构化日志** | 有了 usage 和认证，监控才有意义；此时补成本最低 |
| 6 | 沙箱池化 / TTL / 配额 | 依赖 1、2（要按租户分配、要持久化状态） |
| 7 | 计费 | 依赖 4（usage）和 1（租户） |
| 8 | 桌面端 / 移动端 | 独立战线，不阻塞平台化 |

**核心判断：1 → 2 → 3 是硬顺序，绕不过去。** 4 和 5 可以并行。计费永远排最后，因为它纯消费别人的数据。

### 必须说清的三件事

1. **真 key 仍在沙箱里。** 网关造出来了，但 dsh 还是读 `DEEPSEEK_API_KEY` 直连。差一个 per-session env 钩子（每会话签虚拟 key + 注入 base_url）和确认 dsh 认哪个变量名。**这是设计文档 D4 唯一没兑现的一条。**
2. **价格表是占位常量。** `internal/llm/pricing.go` 里明确标注需按最新价目表核对，否则账单数字不可信。
3. **PG 路径没跑过真库。** 本机无 PG 无 brew，SQL 代码按两侧语法写、错误码映射推演过，但只有 SQLite 实测。
