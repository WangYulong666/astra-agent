# Astra Agent —— 通用 Agent 工作台架构设计方案 v1

> **一句话**：Agent 在隔离 microVM 里跑长任务，人在 Web / 桌面 / 手机任意一端下指令、审批、接管、取产出。
> **代号**：Astra Agent。定位：内部生产力工具，先解决"一件事交给 Agent 跑半小时，人不用守着屏幕"。
> **硬约束**（沿用既有红线）：全组件源码可得、自行编译、自行部署；不依赖云厂商托管服务；平台内核组件只认 OSI 许可。

---

## 0. 一页结论

| 层 | 选定 | 理由 | 红线校验 |
|---|---|---|---|
| 沙箱底座 | **CubeSandbox**（Apache 2.0） | KVM microVM，冷启 ~60ms，单节点千级，e2b 协议兼容 | ✅ 可全量私有化 |
| e2b 协议 | **控制面 REST 直连 CubeAPI + 数据面 Connect RPC 直连 envd** | 官方 proto 生成 Go 客户端，零第三方 SDK 依赖 | ✅ Apache 2.0 |
| 后端 | **Go 1.25 + chi + sqlc/pgx** | SSE/长连接/流式转发最省心；事件表写入密集，避开 ORM 反射 | ✅ MIT/Apache |
| 存储 | **PostgreSQL 16** + **SeaweedFS** + **Valkey** | PG 管账本，SeaweedFS(S3) 管产出物，Valkey 管路由与限流 | ✅ 全部 Apache/BSD |
| 事件总线 | **NATS JetStream** | 单二进制、持久流、天然匹配 append-only 事件模型 | ✅ Apache 2.0 |
| 前端 | **React 19 + TS + Vite**，三端共享 core | 契约单一来源，领域逻辑只写一遍 | ✅ MIT |
| 桌面端 | **Wails v2**（Go + WebView） | 原生侧用 Go，可直接复用后端沙箱客户端与事件处理 | ✅ MIT |
| 移动端 | **Expo（RN + react-native-web）** | 与 Web 共享 TS 代码，一套构建出 iOS/Android | ✅ MIT |
| 认证 | **Zitadel**（Apache 2.0） | Go 实现、单二进制、原生 OIDC，比 Keycloak 轻一个数量级 | ✅ Apache 2.0 |

**三个必须先纠正的认知**：

1. **"三端功能对等"必须改成"能力对等、交互分层"**。手机端跑不了 Monaco 和 xterm，硬上只会做出一个三端都难用的东西。对等的是**同一份 API 契约 + 同一份领域状态 + 同一套权限矩阵**，不是同一套 UI。
2. **CubeAPI 不管命令执行**。它只做沙箱生命周期。跑代码、读文件、开终端全在沙箱内的 envd(`:49983`)，走 Connect RPC。方案里如果只接 CubeAPI，会发现"沙箱创建成功了但什么也干不了"。
3. **Agent 循环不应该放进沙箱**。放进去等于把可观测性、配额、审计、模型切换全部交出去。沙箱只当执行器（例外见 §4.1 的 `byo_runtime` 模式）。

## 1. 需求边界

### 1.1 做什么

| 能力 | 说明 |
|---|---|
| 长任务托管 | 提交任务后关闭浏览器，Agent 继续跑；重新打开从断点续看，一条事件不丢 |
| 沙箱执行 | 代码、Shell、文件、PTY 全在隔离 VM 内，宿主机零暴露 |
| 人工接管 | 危险操作挂起等审批；可暂停、改指令、强行中止 |
| 产出物归档 | 生成的文件、报告、镜像统一入对象存储，带签名下载链接 |
| 多端一致 | 三端看到同一份会话、同一份审批队列、同一份产出物 |
| 多租户 | 组织 / 项目 / 成员三级，沙箱与存储按租户硬隔离 |

### 1.2 明确不做（一期）

- 不做通用 SaaS 对外售卖（内部工具，先不碰计费）
- 不做沙箱内可视化 IDE（Monaco 只读 + 编辑器够用，不做 LSP 全家桶）
- 不做跨沙箱分布式任务（一期只保证单沙箱内串行/并行，不做 DAG 调度器）
- 不做自有模型训练/推理，只做 LLM 网关路由

### 1.3 关键质量目标

| 指标 | 目标 | 备注 |
|---|---|---|
| 沙箱冷启动 | P95 < 300ms | 依赖预热池；CubeSandbox 裸冷启 ~60ms |
| 事件端到端延迟 | P95 < 200ms | 沙箱 stdout → 三端可见 |
| 断线重连 | 零事件丢失 | `after_seq` 续传，不依赖内存缓冲 |
| 单任务最长运行 | 24h（可配） | 超过则暂停快照 + 通知 |
| 单节点并发沙箱 | ≥ 500 | 按 2×16C/64G 节点估 |

## 2. 系统架构

### 2.1 分层职责（硬边界）

```
端          只做交互：渲染、输入、订阅事件。不含任何业务判定。
接入层      只做鉴权、限流、协议转换（REST/SSE）。不含业务流程。
控制面      唯一有状态的地方：Agent 循环、任务状态机、审批判定、事件写入。
沙箱层      唯一执行不可信代码的地方。无状态，可整批销毁重建。
```

这条边界的价值：**沙箱层任何节点挂掉，会话状态零损失**。因为状态全在 PG 事件表里，沙箱只是"可重建的执行器"。

### 2.2 进程拆分

| 二进制 | 职责 | 副本 | 说明 |
|---|---|---|---|
| `astra-api` | HTTP/SSE 入口、鉴权、聚合查询 | N | 无状态，可水平扩 |
| `astra-worker` | Run 执行器：Agent 循环 + 工具调用 | N | 按 `run_id` 做一致性哈希，同一 Run 只能有一个 worker 持有 |
| `astra-sandboxd` | 沙箱池管理：预热、健康检查、回收、快照 | 1（选主） | 与 CubeAPI 交互的唯一出口 |
| `astra-gateway` | LLM 网关：多 provider 路由、密钥、配额、计量 | N | 与 worker 分离，便于独立限流 |

**为什么 worker 和 api 分开**：一个 30 分钟的 Run 会占住 goroutine 和沙箱连接，混在 API 进程里会让 P99 抖动。分开后 API 只做"读"，扩缩容互不影响。

**为什么 sandboxd 要单副本选主**：池化决策（预热几个、回收哪个）必须是单点决策，否则多副本会重复创建/重复回收。它的可用性靠 K8s 快速重启 + CubeMaster 自身幂等兜底，不追求高可用——它挂了只影响新沙箱分配，不影响已在跑的 Run。

## 3. 沙箱层：e2b 协议兼容策略（全案最关键的 30 页）

### 3.1 CubeSandbox 的协议剖面

CubeSandbox 不是一个"e2b 全兼容"的黑盒，它把 e2b 的职责切成了两段：

| 通道 | 端口 | 协议 | 谁在服务 | 覆盖 |
|---|---|---|---|---|
| **控制面** | `:3000` | REST（e2b 兼容） | CubeAPI | 创建/查询/销毁/暂停/恢复沙箱 |
| **数据面** | `:49983` | **Connect RPC + protobuf** | 沙箱内 envd | 命令执行、文件读写、PTY、进程管理 |
| 路由 | `:443` | HTTPS + Host 头 | cube-proxy | 把 `49983-<id>.<domain>` 反代到对应沙箱 |

CubeAPI 已实现的 e2b 兼容端点（源码可核）：

```
GET    /health
GET    /sandboxes                     # 支持 metadata 过滤
GET    /v2/sandboxes                  # state/metadata 过滤 + limit 分页
POST   /sandboxes                     # 创建
GET    /sandboxes/:id
DELETE /sandboxes/:id
POST   /sandboxes/:id/pause           # 保留内存快照
POST   /sandboxes/:id/connect
POST   /sandboxes/:id/resume          # Cube 扩展
GET    /sandboxes/:id/logs            # Cube 扩展，v1/v2 两种结构
PUT    /sandboxes/:id/network         # Cube 扩展，运行时替换出网策略
POST   /sandboxes/:id/timeout         # Cube 扩展，-1 = 永不过期
POST   /sandboxes/:id/refreshes       # Cube 扩展，0~3600s
```

**结论**：控制面够用且有富余（`network` / `timeout` 这两个扩展正好补上配额和闲置回收）。

### 3.2 Go 侧怎么接：三条路，选第三条

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 第三方 Go SDK | `github.com/eric642/e2b-go-sdk` | 非官方维护，一上游改 proto 就断；许可需逐个核；出问题只能自己啃 |
| B. 只用 CubeAPI | 通过 CubeAPI 转发命令 | **走不通**，CubeAPI 没有命令/文件端点 |
| **C. 自研薄协议层（选）** | 控制面手写 REST client，数据面用 e2b 官方 proto 生成 Connect 客户端 | 约 600 行，零第三方风险 |

C 的关键依据：e2b 官方仓库 `e2b-dev/envd-connect-example` 就是一个**纯 Go** 的 envd Connect RPC 客户端示例，用 `connectrpc.com/connect` + protobuf。proto 在 `spec/process/process.proto` 和 `spec/filesystem/filesystem.proto`。我们在自己的仓库里 `buf generate` 一次，代码就归自己了。

### 3.3 协议层代码骨架

```go
// internal/sandbox/e2b/exec.go —— envd Connect RPC 客户端
package e2b

import (
    "connectrpc.com/connect"
    processv1 "astra-agent/pkg/envdproto/process"
    processv1connect "astra-agent/pkg/envdproto/process/processv1connect"
)

func (e *executor) Run(ctx context.Context, sb *sandbox.Sandbox, c sandbox.Command, out io.Writer) (*sandbox.ExecResult, error) {
    cli := processv1connect.NewProcessClient(e.http, sb.EnvdURL)

    stream, err := cli.Start(ctx, connect.NewRequest(&processv1.StartRequest{
        Process: &processv1.ProcessConfig{
            Cmd:  c.Cmd,
            Args: c.Args,
            Envs: c.Envs,   // map[string]string
            Cwd:  c.Cwd,    // 字段名以 buf 生成的 pb 为准
        },
    }), connect.WithInterceptors(auth(sb.AccessToken)))
    if err != nil {
        return nil, fmt.Errorf("envd start: %w", err)
    }
    defer stream.Close()

    for stream.Receive() {
        ev := stream.Msg()   // 事件流：stdout / stderr / exit / pty
        switch ev.GetEvent().(type) {
        case *processv1.StartResponse_Stdout:
            out.Write(ev.GetStdout())
        case *processv1.StartResponse_Stderr:
            // stderr 单独管道，前端要区分着色
        case *processv1.StartResponse_Exit:
            return &sandbox.ExecResult{ExitCode: ev.GetExit()}, nil
        }
    }
    return nil, stream.Err()
}

// envd 鉴权：e2b 用 X-Access-Token 头，值随沙箱创建下发
func auth(token string) connect.UnaryInterceptorFunc { /* ... */ }
```

> ⚠️ 上面 `ProcessConfig` 的字段名来自 e2b 官方示例，最终以 `buf generate` 出来的 pb 定义为准。M0 阶段第一件事就是把它跑通。

### 3.4 沙箱生命周期

```
Create ──► hot ──(idle > 5m)──► paused ──(新指令)──► hot
            │                      │
            └──(Run 结束且无后续)───┴──(idle > 24h)──► destroyed
```

| 状态 | 含义 | 资源占用 | 恢复成本 |
|---|---|---|---|
| `hot` | 内存中运行 | 全量 | 0 |
| `paused` | 内存快照落盘（CubeCoW） | 仅磁盘增量 | 数十 ms |
| `destroyed` | 已回收 | 0 | 需重建，工作区靠 volume 恢复 |

**关键设计：Sandbox 与 Session 绑定，不跟 Run 绑定。** 一个会话多轮对话复用一个沙箱，这样 `pip install` 的包、生成的文件、shell 历史都能延续。Run 结束不销毁沙箱，交给池按空闲策略处理。

**预热池**：

```go
type Pool struct {
    template string
    minIdle  int           // 常驻预热数，按模板配置
    maxTotal int           // 硬上限，超出排队
    idle     chan *Sandbox // 就绪沙箱队列
}

// 分配：非阻塞取，取不到现建（降级路径）
func (p *Pool) Acquire(ctx context.Context) (*Sandbox, error) {
    select {
    case sb := <-p.idle:
        if p.healthy(sb) { return sb, nil }
        p.discard(sb)  // 坏的直接丢，不修补
    default:
    }
    return p.create(ctx)   // 慢路径，打点上报
}
```

### 3.5 出网与安全

这是 Agent 工作台真正的风险面——**沙箱是唯一能访问外网的地方，也是唯一能外泄数据的地方**。

| 措施 | 实现 | 目的 |
|---|---|---|
| 出网白名单 | `PUT /sandboxes/:id/network` 按 Run 下发策略 | 只允许 npm/pypi/github 等必需域名 |
| 分层策略 | 模板级默认 → 项目级覆盖 → Run 级收紧（取交集） | 越用越严，不能越用越宽 |
| 凭据隔离 | 密钥不进沙箱环境变量，由 cube-egress 侧注入 | 沙箱内 `env` 拿不到 token |
| 全量审计 | 所有出网请求记 `(run_id, host, method, bytes)` | 事后可追溯 |
| 默认拒 | 未在白名单内一律拒，不静默放行 | 宁可任务失败，不可静默外泄 |

## 4. Agent 运行时

### 4.1 双模式（这是产品差异点）

| 模式 | Agent 循环在哪 | 适用 | 控制力 |
|---|---|---|---|
| `managed`（默认） | **Go 控制面** | 平台自带工具集，标准化任务 | 全量可观、可审计、可换模型 |
| `byo_runtime` | **沙箱内**（Claude Code / Codex CLI / 自研） | 用户已有 CLI agent，平台只做编排 | 只观测 PTY 输出，审批靠 wrapper 拦截 |

`managed` 模式的价值：工具调用在控制面执行，意味着**每一次 `rm -rf` 都会经过审批中间件**，而不是靠事后审计发现。

`byo_runtime` 模式必须有，否则用户会绕过平台直接在服务器上跑 CLI agent。做法：

```
沙箱内 → init 进程注入 PATH 垫片（shim）
       → 危险命令先 POST 到控制面 /approvals 挂起
       → 审批通过才真正 exec
```

垫片只拦 `rm` / `mv` / `curl` / `ssh` / `git push` 这类高危动词，不追求全覆盖，覆盖率 80% 就够挡住事故。

### 4.2 工具集（managed 模式）

| 工具 | 落到哪 | 风险级 | 默认是否需审批 |
|---|---|---|---|
| `exec_command` | envd process RPC | 按命令内容判 | 命中危险词才审批 |
| `read_file` / `list_dir` | envd filesystem RPC | 低 | 否 |
| `write_file` | envd filesystem RPC | 中 | 覆盖已存在文件时审批 |
| `open_pty` | envd process RPC | 高 | 是 |
| `publish_artifact` | 控制面 → SeaweedFS | 低 | 否 |
| `web_fetch` | 控制面代发（沙箱不出网） | 中 | 域名不在白名单时审批 |

**`web_fetch` 走控制面而不是沙箱**：这样抓取内容统一过滤（防提示注入），且不占用沙箱出网额度。

### 4.3 危险操作拦截

```go
// 分三级，不是二值
type RiskLevel int

const (
    RiskLow  RiskLevel = iota // 直接执行
    RiskMid                   // 执行但记审计
    RiskHigh                  // 挂起等审批
)

func Classify(c Command) RiskLevel {
    switch {
    case matches(c, `rm\s+-rf\s+/($|\s)`), matches(c, `mkfs`),
         matches(c, `dd\s+of=/dev/`), matches(c, `git\s+push.*--force`):
        return RiskHigh
    case matches(c, `^(rm|mv)\s`), matches(c, `chmod\s+777`),
         strings.Contains(c.Raw, "curl"), strings.Contains(c.Raw, "ssh"):
        return RiskMid
    }
    return RiskLow
}
```

审批不是"点一下通过"就完事——要带**上下文**：完整命令、工作目录、影响的文件列表、Agent 的意图说明。审批人在手机上要能三秒判断。

### 4.4 长任务的三个必须

| 问题 | 解法 |
|---|---|
| 上下文窗口爆炸 | 工具输出先落盘成 artifact，只把摘要 + 指针回灌上下文；超过阈值的 stdout 自动截断并标记 |
| 单次 Run 太久 | 强制 checkpoint：每 N 步写一条 `checkpoint` 事件，worker 挂掉可从最近 checkpoint 重建上下文 |
| 用户中途改主意 | 支持"打断注入"：Run 在跑时插入新指令，作为高优先级消息进入下一轮循环 |

## 5. 事件流：三端对等的技术前提

**这是整个设计里最容易被做错的地方。** 如果会话状态挂在 WebSocket 连接上，那么换设备、刷新页面、网络抖动都会导致状态丢失，"三端对等"就是空话。

### 5.1 设计原则：连接与会话解耦

```
错误做法：内存里维护 []Message，通过 WS 广播给所有连接
正确做法：事件先写 PG（append-only），推送只是"加速通知"
```

任何一端在任何时刻接入，都能用 `after_seq` 拿到完整历史。推送通道挂了不影响正确性。

### 5.2 表结构

```sql
CREATE TABLE runs (
    id           uuid PRIMARY KEY,
    session_id   uuid NOT NULL,
    org_id       uuid NOT NULL,
    status       text NOT NULL,        -- queued|running|waiting_approval|paused|completed|failed|cancelled
    next_seq     bigint NOT NULL DEFAULT 1,   -- 事件序号分配器
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE run_events (
    run_id     uuid   NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
    seq        bigint NOT NULL,
    type       text   NOT NULL,   -- message|tool_call|tool_result|stdout|stderr|exit|approval_req|artifact|checkpoint|error
    payload    jsonb  NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (run_id, seq)
);

CREATE INDEX idx_events_created ON run_events (run_id, created_at DESC);
```

**seq 分配方式**（避免并发写乱序）：

```sql
-- 单条 SQL 原子分配，无锁竞争，无间隙
UPDATE runs SET next_seq = next_seq + 1, updated_at = now()
WHERE id = $1
RETURNING next_seq - 1;
```

不用 `MAX(seq)+1`（写放大 + 竞争），也不用 UUIDv7（无法保证同 Run 内连续）。连续序号是断线续传的前提。

### 5.3 订阅协议

```
GET /v1/runs/{run_id}/events?after_seq=42
Accept: text/event-stream

event: stdout
id: 43
data: {"stream":"stdout","chunk":"Building...\n"}

event: approval_req
id: 44
data: {"approval_id":"...","command":"rm -rf /data","risk":"high"}
```

| 特性 | 实现 |
|---|---|
| 断线续传 | 客户端记住最后 `id`，重连带 `after_seq` |
| 多端同时观看 | 无状态 fanout，各端独立订阅，互不影响 |
| 回放 | `after_seq=0` 全量重放，用于新设备首次打开 |
| 心跳 | 每 15s 发注释行 `: ping`，防中间层超时断连 |
| 背压 | 单连接缓冲 512 条，超出则断开让客户端重连续传（不丢数据，只是慢） |

**为什么用 SSE 不用 WebSocket**：事件流是单向的，SSE 自带重连 + `Last-Event-ID` 语义，过反向代理/企业网关比 WS 稳，且能用标准 HTTP 鉴权。上行操作（发指令、审批）走普通 POST。只有 PTY 需要双向，那条单独走 WS。

### 5.4 Run 状态机

```
queued ──► running ──┬──► completed
   │           │  ▲   ├──► failed
   │           │  │   └──► cancelled
   │           ▼  │
   │      waiting_approval ──(拒绝)──► running（带拒绝原因回灌）
   │           │
   └───────────┴──► paused ──(恢复)──► running
```

不变量（写进代码断言，不靠约定）：
- `completed/failed/cancelled` 是终态，不可逆
- 同一 Run 同时只允许一个 worker 持有（PG advisory lock）
- `waiting_approval` 状态下 worker 释放执行权，只保留上下文

## 6. 三端方案

### 6.1 共享什么、不共享什么

这是"三端功能对等"落地时的真实边界：

| 资产 | Web | Desktop | App | 说明 |
|---|---|---|---|---|
| API 类型 / client | ✅ 共享 | ✅ | ✅ | 由 `contracts/openapi.yaml` 生成 |
| 领域状态机 / hooks | ✅ 共享 | ✅ | ✅ | `packages/core` |
| 业务校验（zod） | ✅ 共享 | ✅ | ✅ | 与服务端同源 |
| 路由 | 各自 | 各自 | 各自 | 三端导航范式不同，强行统一是负收益 |
| UI 组件 | shadcn | shadcn | RN 原生组件 | 复用率 ~30%，别硬凑 |
| 代码编辑器 | Monaco | Monaco | 只读 diff | 手机不做编辑 |
| 终端 | xterm.js | xterm.js | 不支持 | 手机只显示最近输出 |
| 文件系统桥 | ❌ | ✅ 原生能力 | ✅ 系统分享 | 桌面端独有价值 |

### 6.2 桌面端选型

| 维度 | **Wails v2** | Tauri 2 | Electron |
|---|---|---|---|
| 原生侧语言 | **Go** | Rust | Node |
| 复用后端代码 | **✅ 直接 import** | ❌ 要重写 | ⚠️ 要移植 |
| 安装包体积 | ~12MB | ~8MB | ~120MB |
| 内存占用 | 低 | 低 | 高 |
| 生态成熟度 | 小 | 大 | 最大 |
| 许可 | MIT | MIT/Apache-2.0 | MIT |

**选 Wails v2**，决定性理由只有一条：**桌面端能直接 `import` 后端的 `sandbox` / `events` 包**。这意味着"本地目录挂载进沙箱""离线缓存事件""本机跑一个轻量 worker"这些能力，在桌面端是复用而不是重写。Tauri 虽然生态更好，但要把这些逻辑用 Rust 再写一遍，团队是 Go 栈，不划算。

> 风险：Wails 社区小，遇到 WebView 兼容坑要自己填。退路是 Tauri 2，代价是原生层重写。

### 6.3 移动端取舍（明确说清"不对等"的部分）

手机端做三件事，做好就够：

1. **审批**：推送通知 → 点开看到命令 + 上下文 → 一键通过/拒绝
2. **查看**：任务进度、最近输出、产出物预览
3. **下指令**：语音转文字 + 简短文本，发起新任务

不做：代码编辑、终端交互、多文件对比。硬做出来的东西没人用。

## 7. 数据模型

```
orgs ──┬── members ── users
       └── projects ──┬── sessions ── runs ── run_events
                      ├── sandboxes
                      ├── artifacts
                      └── templates

approvals ── run_id
usage_records ── org_id（LLM token、沙箱秒数）
audit_logs ── org_id（出网、审批、管理操作）
```

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sessions` | id, project_id, title, sandbox_id, last_active_at | 一个会话绑一个沙箱 |
| `runs` | id, session_id, status, next_seq, mode | `mode`: managed / byo_runtime |
| `sandboxes` | id, provider_id, template, state, envd_url, expires_at | `provider_id` 是 CubeSandbox 的 sandboxID |
| `artifacts` | id, run_id, path, size, sha256, storage_key | 内容在 SeaweedFS，PG 只存元数据 |
| `approvals` | id, run_id, kind, payload, status, decided_by, decided_at | 待审批进 `waiting_approval` |
| `templates` | id, name, image, tools[], egress_policy | 版本化，不可变，改则新建 |

**审计表单独放**：`audit_logs` 只追加不删，按月分区，保留 1 年。它是出事时唯一能说清"谁在什么时候让 Agent 干了什么"的东西。

## 9. 关键 API

```
POST   /v1/sessions                          创建会话（分配沙箱）
GET    /v1/sessions/:id
POST   /v1/sessions/:id/runs                 提交指令，返回 run_id
GET    /v1/runs/:id                          查询状态
GET    /v1/runs/:id/events?after_seq=N       SSE 订阅
POST   /v1/runs/:id/cancel
POST   /v1/runs/:id/messages                 运行中注入指令
GET    /v1/runs/:id/approvals                待审批列表
POST   /v1/approvals/:id/decide              {approve|reject, comment}
GET    /v1/runs/:id/artifacts
POST   /v1/artifacts/:id/download-url        签名链接（60s）
WS     /v1/sandboxes/:id/pty                 终端（仅 web/desktop）
GET    /v1/templates
POST   /v1/templates                         管理端
```

约定：
- 所有列表接口游标分页（`cursor` + `limit`），不用 offset
- 所有写操作幂等键 `Idempotency-Key`，防手机端重试重复提交
- 错误体统一 `{code, message, trace_id}`，`trace_id` 直接可查链路

## 10. 部署拓扑

```
┌─ K8s（控制面池，可弹性）──────────────────────┐
│  api × N   worker × N   gateway × N          │
│  sandboxd × 1（选主）                         │
│  PG(主从)  NATS(3节点)  Valkey  Zitadel      │
└──────────────────┬────────────────────────────┘
                   │ 内网
┌─ 沙箱节点池（裸金属 / 支持嵌套虚拟化的实例）──┐
│  必须 x86_64 + /dev/kvm                       │
│  CubeMaster + Cubelet + cube-proxy + CubeVS   │
│  每节点 500~1000 microVM                      │
└───────────────────────────────────────────────┘
```

**硬性前提**：CubeSandbox 需要 x86_64 + KVM。你的 Mac Mini M4（arm64，无 KVM）**不能跑**，所以：

| 环境 | 沙箱 provider |
|---|---|
| 本地开发（mac） | `docker` provider（Docker + 受限容器，功能等价但无 VM 隔离） |
| 测试/预发 | 一台 x86_64 带 KVM 的机器 |
| 生产 | 沙箱节点池 |

`provider` 接口存在的最大价值就是这个——**开发机不用为了跑起来去搞一台 KVM 机器**。

## 11. 分期路线

### M0 · 协议验证 Spike（1~2 周，必须先做）

这是全案唯一的技术赌博点，**验证不过就不要往下走**。

| # | 验证项 | 通过标准 |
|---|---|---|
| 1 | CubeSandbox 单机部署 | x86_64 KVM 机器上 `CubeAPI` 起来，`/health` 通 |
| 2 | e2b Python SDK 跑通 | 官方 SDK 零改动执行 `print(1+1)` 成功（证明兼容声称属实） |
| 3 | **Go + envd Connect RPC 跑通** | 用生成的 proto 执行 `/bin/bash -c "echo hi"` 拿到 stdout |
| 4 | 文件读写 | `WriteFile` → `ReadFile` → `ListDir` 全通 |
| 5 | PTY | 开一个交互式 session，能收发 |
| 6 | pause/resume | pause 后 resume，**内存里的变量还在**（验证快照语义） |
| 7 | 冷启动实测 | 预热池 vs 冷建，各 100 次，出 P50/P95 |
| 8 | 出网策略 | `PUT /network` 生效，白名单外的域名被拒 |
| 9 | 多租户隔离 | 两个沙箱互相看不到对方文件系统、网络不可达 |

任一项不过 → 回到选型阶段重新评估（备选：Firecracker 直驱 / gVisor / Kata）。

### M1 · 最小闭环（4~6 周）

- `astra-api` + `astra-worker` + `astra-sandboxd`
- managed 模式 Agent 循环 + 4 个工具（exec / read / write / list）
- 事件表 + SSE 订阅 + 断线续传
- Web 端：会话列表、对话流、输出流、产出物下载
- 单租户，无审批

**验收**：一个人能在 Web 上让 Agent 跑完一个"下载 CSV → 清洗 → 出图 → 给下载链接"的任务，中途刷新页面不丢任何输出。

### M2 · 桌面端 + 本地能力（3~4 周）

- Wails v2 壳，复用 web 构建产物
- 本地目录挂载进沙箱（拖一个文件夹进去，沙箱内可见）
- 离线事件缓存（断网时看历史，恢复后补齐）
- 系统通知（任务完成 / 待审批）

### M3 · 审批 + 移动端（3~4 周）

- 风险分级 + 审批流转 + 审计表
- Expo App：审批队列、推送通知、任务查看、语音指令
- byo_runtime 模式（PTY 编排 + shim 拦截）

### M4 · 多租户与治理（4~6 周）

- 组织/项目/成员、权限矩阵
- 模板版本治理、出网策略分层
- LLM 网关配额与计量
- 沙箱池调优、闲置回收、成本看板

**总计约 4~5 个月到可用**（M0~M2 是 2 个月出可演示版本）。

## 12. 风险清单

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | CubeSandbox 的 envd 版本与 e2b 上游漂移 | Go 客户端某天编译失败 | proto 拷进自己仓库，锁定 commit；升级当独立任务做 |
| 2 | 开发机无 KVM | 本地跑不起沙箱 | `docker` provider 降级，接口隔离 |
| 3 | 出网 = 数据外泄通道 | 合规事故 | 白名单默认拒 + 全量审计 + 凭据不进沙箱 |
| 4 | 事件表无限增长 | PG 膨胀 | 按月分区，超 90 天的 Run 事件转 SeaweedFS 冷存 |
| 5 | 三端并行拖慢进度 | M1 延期 | M1 只做 Web，桌面/移动严格后置，不并行 |
| 6 | LLM 成本失控 | 账单 | 网关硬配额 + 单 Run token 上限 + 超限自动暂停 |
| 7 | Wails 生态坑 | 桌面端卡住 | 预留 Tauri 退路，桌面端功能面收窄（不做 IDE） |
| 8 | 提示注入导致 Agent 执行危险命令 | 安全事故 | 审批中间件 + 出网白名单 + 沙箱隔离三重兜底 |
