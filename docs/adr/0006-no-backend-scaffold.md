# 0006. 不引入开源后台脚手架作为基座

- **状态**：已采纳
- **日期**：2026-10-28
- **相关**：`docs/部署与流水线方案.md` §管理后台

## 背景

需要一个管理后台（租户、配额、模板、审计）。可选的开源脚手架都挺成熟，直接拿来用看起来能省很多时间：

| 项目 | 许可 | 体量 | 自带能力 |
|---|---|---|---|
| gin-vue-admin | Apache 2.0 | 25k star，2026-09 仍活跃 | 用户 / 角色 / 菜单 / 部门 / 代码生成器 / 多租户版 |
| go-admin | MIT | 12.7k | 多租户 + Casbin + 多套 UI |
| Vben Admin | MIT | 大 | 纯前端 Vue3 + TS，表格表单强 |
| GoAdminGroup/go-admin | Apache 2.0 | 9k，2025-06 后停更 | 不做基座 |

## 决策

**不把 astra 换成后台脚手架。** 采用：

```
Vben Admin（前端，MIT）
  + astra-api 增加 /admin 模块（复用现有服务与中间件）
  + Casbin（后端 RBAC）
```

一套 RBAC、单二进制、审计统一。

### 为什么不能整包引入

脚手架自带用户 / 角色 / 菜单 / 部门，但 **ACP 连接、沙箱生命周期、审批流转一个都没有**。整套引入的必然结果是：

- **两套 RBAC**：脚手架的菜单权限 + astra 的租户/资源权限，边界立刻糊掉
- **两套用户表**：登录走哪边？会话归属谁的租户？
- **两套审计**：谁批准了这条危险命令——查哪张表？
- **两套部署单元**：多一个服务、多一套探针、多一套配置

省下来的是 CRUD 页面，付出的是架构边界。

### 管理后台与管理链路的边界

| 管理后台管 | 不走管理后台 |
|---|---|
| 租户、配额、模板版本、审计查询 | 会话执行链路（astra-api / worker） |
| 用户与角色 | ACP 连接与沙箱生命周期 |
| 系统配置 | 事件流 |

管理后台只碰**配置数据**，不碰**运行时链路**。

## 后果

### 好的

- 权限模型只有一套，审计只有一处
- 单二进制交付：前端 SPA 用 `go:embed` 打进 `astra-api`，不单独起 nginx（省一个 Deployment，也省掉「静态资源版本和 API 版本对不上」）
- 后台改动不影响执行链路

### 坏的

- **前期慢**：租户 / 角色 / 菜单这些页面要自己写，比 `git clone` 一个脚手架多花约 1~2 周
- 依赖 Vben Admin 的升级节奏（MIT，风险低但不是零）
- 团队若熟悉 gin-vue-admin，会有学习成本

## 被否掉的替代方案

| 方案 | 否掉的原因 |
|---|---|
| gin-vue-admin 整包做基座 | 两套 RBAC / 用户表 / 审计，架构边界糊掉。开发速度快但技术债在第一个月就到期 |
| go-admin 做基座 | 同上，另外它的多租户模型与我们「会话即租户边界」的语义不同 |
| GoAdminGroup/go-admin | 2025-06 后停更 |
| Ant Design Pro | 可用，但 Vue 生态与团队既有（Astra 系列是 Vue3）不一致，无收益 |

## 例外

**如果要求在两周内看到可用后台**，才用 gin-vue-admin 起一个独立的 `astra-admin` 服务，但必须：

1. 明确它只做「租户/配额/审计查询」，不接执行链路
2. 记一笔技术债：两套 RBAC 需要同步机制
3. 在 ADR 里新开一条说明这个临时决策，以及回退路径
