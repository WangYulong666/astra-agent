# Astra 部署与流水线方案 v1（k8s + APISIX）

> 2026-10-28。前置：`架构设计方案.md` 定的 4 个 Go 二进制（api / worker / sandboxd / gateway）+ CubeSandbox 沙箱 + dsh ACP agent。
> 本文只解决「怎么部署、怎么发版、管理后台用什么」。

---

## 0. 一页结论

| 项 | 定案 | 理由 |
|---|---|---|
| 集群 | **k3s**（生产可换 RKE2） | Apache 2.0，单二进制，内置 etcd；**禁用自带 traefik**，入口交给 APISIX |
| 入口 | **APISIX（Ingress Controller + Gateway API）** | Apache 2.0，插件化限流/鉴权，SSE 长连接可控 |
| 负载 | **MetalLB** 给 APISIX 一个 VIP | Apache 2.0，裸机/自建集群没有云 LB |
| 沙箱 | **CubeSandbox 官方 Helm**，独立 node pool | v0.7.0 有 Chart，但计算面要 privileged + `/dev/kvm` |
| 镜像仓 | **Harbor** | Apache 2.0，自部署，带签名/扫描 |
| GitOps | **ArgoCD** | Apache 2.0，镜像 tag 变更在 git 里可审可回滚 |
| 前端 | **Vben Admin**（Vue3 + TS） | MIT，表格/表单密集的管理后台最省事 |
| 管理 API | **astra-api 内加 admin 模块 + Casbin** | 不引整套脚手架，避免与 4 服务架构冲突 |

**一个必须提前知道的分歧点**：CubeSandbox on k8s 官方仍标 **Preview**，且要求 privileged + 独立 XFS 数据盘 + `/dev/kvm`。
M0 阶段（验证沙箱 + ACP 协议）用单机 compose 能省 3–5 天；k8s 从 M1 起上。**但 manifest 可以从第一天就写好**，M0 用 compose 跑通协议、M1 直接切 k8s，切换成本只是换一次 `sandbox provider` 配置。

## 1. 集群拓扑

### 1.1 发行版：为什么 k3s 而不是 kubeadm / TKE

红线是「全套源码可控自部署」，所以 **TKE / ACK / EKS 直接排除**。剩下三个：

| 选项 | 许可 | 取舍 |
|---|---|---|
| **k3s** | Apache 2.0 | 单二进制，内置 etcd/sqlite，默认组件轻；**自带 Traefik 要显式关掉** |
| RKE2 | Apache 2.0 | CIS 合规、默认安全加固，适合等保场景。生产阶段可平滑替换 |
| kubeadm | Apache 2.0 | 最原生，但证书轮转、升级、etcd 运维全得自己写，不划算 |

⇒ 起步用 k3s，若客户要等保/CIS 出报告，换 RKE2（同属 Rancher，迁移成本低）。

### 1.2 节点规划

| 池 | 数量 | 规格 | 职责 | 调度约束 |
|---|---|---|---|---|
| control | 3 | 4c8g | k3s server + etcd + APISIX + 基础设施 | 常规 |
| app | 2+ | 8c16g | astra-api / worker / gateway、PG、Valkey、EMQX、SeaweedFS | 常规 |
| **cube** | 1+ | 16c32g，**x86_64 + KVM + 独立 XFS 盘** | CubeSandbox 计算面（Big Pod） | `label: astra.io/cube-node=true`<br>`taint: astra.io/cube-node=true:NoSchedule` |

cube 池必须独立：计算面是 privileged pod，不能和业务混跑；且 Cube 的 overcommit 逻辑与 k8s 的资源模型会打架。

### 1.3 命名空间

```
astra-system     astra-api / worker / sandboxd / gateway、APISIX
astra-data       PG、Valkey、SeaweedFS、EMQX 5.8
astra-cube       CubeAPI / CubeMaster / CubeProxy / cube-node DaemonSet
astra-ops        ArgoCD、Harbor、监控
```

**为什么不把 Cube 放 astra-system**：cube 的 PodSecurity 必须是 privileged，而业务 ns 应该开 baseline/restricted。混在一起等于白设。

## 2. CubeSandbox on k8s

### 2.1 组件映射（官方 Chart v0.7.0）

| Cube 组件 | k8s 形态 | 关键 |
|---|---|---|
| cubelet + network-agent + cube-egress + CubeShim + CubeHypervisor | **DaemonSet（Big Pod）** | privileged + hostPID + hostPath `/dev/kvm`、`/data/cubelet`；**沙箱跑在 Big Pod 内部** |
| CubeAPI / CubeMaster / CubeProxy | Deployment + Service | CubeMaster 挂 PV 存模板，**不能丢** |
| MySQL / Redis | StatefulSet | 建议换 **PG + Valkey**（对齐现有选型和许可红线） |
| CoreDNS | 复用集群 CoreDNS | 加 `cube.app` 转发 |

### 2.2 四个已经踩过的坑（openFuyao / Alva 实践，直接抄结论）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 同节点访问沙箱映射端口不通 | eBPF 转发本节点流量未填伪首部 → checksum 校验失败 | v0.4.0 已修（PR #469）。**低于 v0.7.0 别用** |
| 2 | cubelet 进 pod 后容器崩 | cubelet 的设计是「杀父进程自己变孤儿」，与 PID 1 冲突 | `tini` 作 PID 1 + entrypoint 后台起 cubelet + pidfile + preStop |
| 3 | host-mount 的 "host" 变成 Big Pod 而非节点；CubeVS 默认拒绝网段覆盖了 k8s pod CIDR | 语义漂移 | 计算面 pod 必须 hostPath 直通；**显式 allow_out 集群 Service CIDR 和 pod CIDR** |
| 4 | k8s 调度 pod、CubeMaster 调度沙箱，两套调度器互相踩 | 资源模型冲突 | **计算面 pod 的 `resources.limits` 给足或不设**，否则 Cube 的 overcommit 被 cgroup 卡死 |

### 2.3 仍然存在的风险（官方自己标注的）

- **Preview 状态**：资源紧张时驱逐、计算节点升级会中断存量沙箱、cube-node pod 重建导致沙箱网络中断
- **「60ms 冷启动」不是端到端 SLO**：实测 GKE 上 `Sandbox.create` p50 ≈ 0.23s，完整生命周期 ≈ 0.78s
- 模板镜像架构必须显式指定 `linux/amd64`，否则在 Apple Silicon 上同步镜像会拿到错架构 rootfs，且**模板仍显示 READY**，直到 restore 才失败

⇒ 平台侧必须假设沙箱会随时消失：会话状态全在 PG，`session_sandbox_history` 记录重建。这一点 v2 已经设计好了。

## 3. APISIX 网关

### 3.1 部署形态

用 **APISIX Ingress Controller + Gateway API**（不是传统 Ingress 注解）。官方明确：k8s 内推荐 CRD，新部署推荐 Gateway API。

```
控制面：apisix-ingress-controller（watch Gateway/HTTPRoute/ApisixRoute）
数据面：apisix Deployment × 2+（Nginx + LuaJIT）
配置库：etcd × 3（Apache 2.0）
外部入口：MetalLB 给 apisix Service 一个 VIP
```

数据面与控制器分开扩缩：流量涨扩数据面，配置多扩控制器无意义。

### 3.2 路由设计（Astra 特有）

| 路径 | 上游 | 特殊配置 |
|---|---|---|
| `/v1/*` | astra-api | JWT 鉴权、按 tenant 限流 |
| `/admin/*` | astra-api（admin 模块） | JWT + RBAC（Casbin） |
| `/v1/runs/:id/events` | astra-api | **SSE：关 buffering、读超时 3600s**，不能走默认 60s |
| `/v1/sessions/:id/terminal` | astra-api | **WebSocket**，需 `timeout` 与升级头透传 |
| `/webhooks/*` | astra-gateway | IP 白名单，不走 JWT |

**SSE 是最容易翻车的点**：APISIX 默认 `proxy_buffering on` + 60s 超时，表现是「事件流卡住不推送、一分钟后断开」。必须在路由上显式关掉缓冲并拉长读超时。

### 3.3 限流与配额

限流 key 用 `tenant_id`（从 JWT claim 取），不是 IP —— 同一租户可能多端并发。

```yaml
# limit-count 按租户：1000 req/min，超了 429
plugins:
  limit-count:
    count: 1000
    time_window: 60
    key_type: var
    key: http_x_tenant_id
    rejected_code: 429
```

**注意**：LLM 调用配额不该在网关做（一次 run 可能几十次模型调用，网关看不到），要放在 astra-gateway 的租户令牌里。网关只管请求级限流。

### 3.4 沙箱出网不走 APISIX

沙箱内 agent 的出网由 **CubeEgress 白名单**管（`PUT /sandboxes/:id/network`），与 APISIX 无关。agent 的 LLM 只允许指向 astra-gateway 的集群内地址 —— 这条规则在 Cube 的网络策略里，不在网关。

## 4. 流水线

### 4.1 阶段

```
lint/test ──► build ──► image ──► sign ──► GitOps ──► smoke
  │            │         │        │         │          │
go vet      Go 4 二进制  Harbor   cosign   ArgoCD    verify-acp
pnpm lint   前端 SPA    推送      (可选)   改 tag     + 健康检查
```

### 4.2 构建要点

**Go 侧**：4 个二进制用 `-trimpath -ldflags="-s -w"` 静态编译，运行镜像用 **distroless/static 或 scratch**，单镜像 15–25MB。不装 ca-certificates 之外的任何东西。

**前端侧**：SPA 构建产物用 Go 1.16+ 的 `embed` **直接打进 astra-api**，不单独起 nginx。省一个 Deployment、一个 Service、一套静态资源版本对齐。

**镜像 tag 规则**：`<git-sha 短>` 为主标签，`<semver>` 和 `latest` 为辅 —— ArgoCD 追踪 git-sha，回滚就是改回上一个 sha。

### 4.3 部署：GitOps 而非 CI 直连集群

CI 不持有 kubeconfig。CI 只做「构建镜像 + 更新 `deploy/overlays/<env>/kustomization.yaml` 里的 image tag 并提交」，ArgoCD 检测 git 变更后同步。

好处：**集群里跑的每个版本都能对到一次 git commit**，回滚是 `git revert`，不是"再跑一次流水线"。

### 4.4 CI 引擎的选择（这里有个红线冲突，需要你拍板）

| 选项 | 许可 | 与红线的关系 |
|---|---|---|
| **CNB**（现在在用） | 腾讯云托管服务 | ⚠️ **严格按「不依赖云厂商托管」的红线，CNB 不合格**。代码和构建日志都过云 |
| Gitea + Woodpecker | Gitea MIT / Woodpecker Apache 2.0 | 完全自部署，符合红线 |
| Gitea + Tekton | Apache 2.0 | 更重，但 k8s 原生，构建即 Pod |

**我的判断**：如果 Astra 是内部工具/自用，CNB 继续用没问题（你已经有一整套 Astra 流水线在跑，切换成本不低）。但如果要卖给客户、要过合规审查，**CI 必须自建** —— 因为「源码可控」的审查方会问"你的代码托管在哪、构建在哪执行"，答"腾讯云"就直接出局。

⇒ 建议：M1–M3 继续 CNB（快），**M4 多租户/治理阶段切 Gitea + Woodpecker**。流水线的 Pipeline 定义写成两边都能跑的形态（就是普通 shell 步骤，别用 CNB 专属语法）。

### 4.5 环境分层

| 环境 | 集群 | 数据 | 触发 |
|---|---|---|---|
| dev | 单节点 k3s | sqlite / 单机 PG | push 即部署 |
| staging | 3 节点 | 独立 PG，脱敏数据 | 合入 main |
| prod | 3+ 节点 + cube 池 | 独立 PG + 备份 | 手动 approve |

## 5. 开源选型：Go 后端与前端管理面板

### 5.1 候选（2026-09 快照，许可已核）

| 项目 | 技术栈 | 许可 | 体量 | 适合 |
|---|---|---|---|---|
| **gin-vue-admin** | Gin + Vue3 + Vite | **Apache 2.0** | 25k star，2026-09 仍活跃 | 一体化后台，带多租户版、代码生成器、插件市场 |
| **go-admin** | Gin + Vue + 多 UI | **MIT** | 12.7k star，2026-09 活跃 | 多租户 + Casbin + 代码生成，前端可选 Element/Arco/AntD |
| GoAdminGroup/go-admin | 数据面板 builder | Apache 2.0 | 9k star，2025-06 后停更 | 给已有 Go 服务挂数据面板，**不建议做基座** |
| Simple Admin Core | go-zero + Vben | Apache 2.0 | 2k star | 微服务 + K8s 治理路径 |
| **Vben Admin** | Vue3 + Vite + TS + Ant Design Vue | **MIT** | 大 | 纯前端管理壳，表格/表单能力强 |
| Ant Design Pro | React + Umi | MIT | 大 | React 团队；与 Umi 深度绑定，较重 |

### 5.2 关键判断：不要把 astra 换成后台脚手架

`gin-vue-admin` / `go-admin` 都是**单体后台脚手架**，自带用户/角色/菜单/部门/日志 + 代码生成器。而 astra 的核心是 **ACP 连接、沙箱生命周期、审批流转、事件流** —— 这些它们一个都没有。

如果整套引入，会出现两套 RBAC、两套用户表、两套审计，边界立刻糊掉。

**正确切法**：管理后台是**外围**，只碰「租户、用户、配额、模板、审计查询、设备/报告元数据」；会话执行链路完全走 astra-api/worker。

### 5.3 推荐组合

**A（推荐，稳妥）**

```
前端   Vben Admin（独立 SPA，部署为静态站点或 embed 进 api）
后端   astra-api 内加 /admin 模块
       ├─ 用户/角色/权限：Casbin（Apache 2.0）+ PG
       ├─ 菜单/动态路由：前端 Vben 配置驱动，后端只给权限位
       └─ CRUD 提速：抄 gin-vue-admin 的代码生成器思路，或直接用 goctl/ent 生成
```

优点：一套 RBAC、一套用户、单二进制、审计统一。缺点：CRUD 页面要自己写（没有现成生成器那么快）。

**B（最快出活）**

```
前端   gin-vue-admin 自带 Vue3
后端   gin-vue-admin 作为独立服务 astra-admin（独立镜像、独立 DB schema）
       只管租户/用户/配额/模板/审计查询，通过 gRPC 或 HTTP 调 astra-api 拿会话数据
```

优点：3 天能出可用后台（用户管理、角色、菜单、操作日志全有）。缺点：两套 RBAC 要同步（用户在 A 改、权限在 B 判），长期是技术债。

⇒ **选 A**。B 只在「老板要求两周内看到管理后台」时才用，并且要明确写进技术债清单。

## 6. 分期落地

| 阶段 | 集群 | 沙箱 | 流水线 | 管理后台 |
|---|---|---|---|---|
| **M0**（2 周） | 单机 docker compose | CubeSandbox compose | 本地脚本 | 无 |
| **M1**（4 周） | k3s 单节点 + APISIX | CubeSandbox Helm（单 cube 节点） | CNB → Harbor → ArgoCD | Vben 骨架 + 登录 |
| **M2**（4 周） | k3s 3 节点 | 多 cube 节点 | 加 staging | 租户/配额/审计 |
| **M3**（4 周） | 同上 + 监控 | 预热池 | 加 prod approve | 模板治理 |
| **M4**（4~6 周） | RKE2（如需等保） | 多租户隔离 | **切 Gitea + Woodpecker** | 完整 RBAC |

**M0 不上 k8s 的理由**：CubeSandbox on k8s 是 Preview，节点预检（KVM、XFS/reflink、bpffs、CIDR 冲突）+ node-init + XFS loopback 至少 3 天，而这 3 天不产生任何协议层结论。M0 的目标是验证「沙箱能不能跑 dsh、ACP 能不能驱动」，用 compose 两小时能起来。

## 7. 风险

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| 1 | **CubeSandbox on k8s 是 Preview** | 升级中断沙箱、驱逐、网络中断 | 会话状态全在 PG；`session_sandbox_history` 可重建；M1 只跑单 cube 节点 |
| 2 | **计算面 privileged + /dev/kvm** | 多数托管 k8s 不允许；等保审查会问 | 独立 node pool + 独立 ns；写进安全说明「计算面与业务面物理/逻辑隔离」 |
| 3 | 两套调度器（k8s + CubeMaster） | 资源争抢、pod 被 OOMKill | 计算面 pod **不设或给足 limits** |
| 4 | **CNB 是云托管，与红线冲突** | 合规审查出局 | M4 切 Gitea + Woodpecker；pipeline 写成通用 shell |
| 5 | SSE 经网关被缓冲/超时 | 事件流卡死 | 路由显式关 buffering + read timeout 3600s，需专门压测 |
| 6 | etcd 成为单点 | APISIX 配置不可写 | 3 副本；或改 standalone 模式去掉 etcd |
| 7 | 镜像仓库单点 | 无法拉镜像、无法发布 | Harbor 主从 + 本地缓存层；ArgoCD 保留上一版本镜像 |
